# Мобильный клиент «График приступов»

> Статус: предложение (без кода). Отдельный репозиторий, не этот Laravel-проект.
> Серверный контракт уже есть: JSON API `/api/v1` (Sanctum + refresh, seizures create/list/update/delete).

## 1. Зачем этот документ

Нужен Android-клиент, чтобы быстро опробовать API и закрыть основной сценарий из концепта: **нажал — отправилось**.

Параллельно нужен полнофункциональный журнал на телефоне. Казалось бы, это два приложения. Ниже — почему это один Expo-проект с двумя иконками, и как он должен себя вести.

## 2. Решение

| Вопрос | Ответ |
|---|---|
| Платформа на первом этапе | Только Android |
| Стек | **Expo + TypeScript** (React Native) |
| Репозиторий | Отдельный от этого серверного проекта |
| Сколько APK / листингов в магазине | **Один** |
| Как выглядят «два приложения» | Две иконки в лаунчере (`activity-alias`) |
| Общая авторизация | Бесплатно: одно хранилище токенов на процесс |

Полноценное приложение — журнал, фильтры, удаление, профиль/выход.

Второе «приложение» — только авторизация (если нужно) и отправка события спазма, после чего процесс закрывается.

Оба входа — один бинарник. Кто авторизовался через любую иконку, авторизован в обеих.

## 3. Почему не два APK

`expo-secure-store` (и любое обычное хранилище) **не шарится** между пакетами. Логин в одном APK сам по себе не авторизует второе.

Два пакета с общей сессией возможны (общий `ContentProvider` с `protectionLevel="signature"`, одна подпись, EAS development build). Это отдельная нативная работа, Expo Go отпадает, плюс гонка на ротации refresh (см. §7).

Для описанного UX это лишнее. Две иконки в одном APK дают тот же эффект без IPC.

Два листинга в магазине имеет смысл позже — разные аудитории, разные разрешения, отдельная поставка. Пока не нужно.

Что не рассматриваем на старте:

- Flutter, Kotlin/Compose, KMP — медленнее до первой пробы на телефоне;
- Vue + Capacitor — «сайт в оболочке», хуже стыкуется со сценарием одной кнопки;
- генерация клиента из OpenAPI — контракта в репозитории нет, эндпоинтов мало, модели пишем руками.

## 4. Две точки входа

Один проект, одна `applicationId`. В манифесте — основная activity и `activity-alias` со своей подписью и иконкой. Обе с `MAIN` / `LAUNCHER`. Expo: config plugin (alias в манифесте); в Expo Go второй ярлык может не появиться — это нормально для прототипа экранов, для проверки иконок нужен dev/preview build.

Примеры ярлыков: **Журнал** и **Приступ**.

На старте читаем, через какой компонент открыли:

| Вход | Поведение |
|---|---|
| Журнал | Обычный UI: логин при необходимости, список, создание, удаление |
| Приступ | Быстрый путь (§5), затем выход из приложения |

Пользователь может снять вторую иконку с рабочего стола; в списке приложений обе обычно остаются. В Play Store это одно приложение.

## 5. Сценарии «Приступ»

Ключевое требование концепта: быстрый доступ к отправке, редкая повторная авторизация.

```
открыли иконку «Приступ»
        │
        ├─ нет токенов ──► экран входа / регистрации
        │                      │
        │                      ▼
        │                 сохранить токены
        │                      │
        │                      ▼
        └─ есть токены ──► POST /seizures ──► закрыть приложение
```

- Неавторизован: логин или регистрация → отправка события → закрыть.
- Авторизован: отправка → закрыть. Журнал не показывать.
- Тело запроса: `{ "timezone": "<IANA>" }` (например `Europe/Moscow`). Пустой `{}` тоже валиден: сервер запишет «сейчас» в UTC. Пояс лучше слать всегда — так совпадает с задумкой API для мобильного клиента.
- `occurred_at` в быстром пути не передаём: это «приступ прямо сейчас». Задним числом — в журнале.
- После успеха (201) — native `finish()` / выход. Не оставлять пустой экран журнала.
- Ошибка сети или 401 после неудачного refresh — короткий текст и кнопка «повторить» / «войти снова», не молчаливый выход.
- Экран входа в этом потоке тот же, что в журнале. Успешный логин пишет в общее хранилище — журнал при следующем открытии уже с сессией.

## 6. Стек клиента

Минимум, с которого стартовать отдельный репозиторий:

| Слой | Что брать |
|---|---|
| Каркас | Expo (dev build для alias и выхода из activity) |
| Язык | TypeScript |
| Навигация | expo-router: ветка журнала и ветка быстрого входа |
| HTTP | `fetch` или тонкая обёртка (ofetch / ky) |
| Токены | `expo-secure-store` |
| Часовой пояс устройства | `expo-localization` (IANA для `timezone`) |
| UI | что угодно простое; NativeWind, если нужен Tailwind-привычный вид |

Первый вертикальный срез: логин → сохранить токены → кнопка «приступ сейчас» → список. Удаление, фильтр дат, вторая иконка — следующим заходом. Сброс пароля на старте не делать: ссылка с API уходит на веб.

## 7. Контракт API, на который опираемся

База: `{APP_URL}/api/v1`. JSON. Защищённые методы: `Authorization: Bearer <access_token>`, плюс `Accept: application/json`.

Обёртка ресурсов Laravel: поля сущности в `data`. Список — `data` + `meta` + `links`.

### Авторизация

| Метод | Путь | Тело | Успех |
|---|---|---|---|
| POST | `/register` | `name`, `email`, `password`, `password_confirmation`, `timezone?` | 201, пара токенов |
| POST | `/login` | `email`, `password` | 200, пара токенов |
| POST | `/token/refresh` | `refresh_token` | 200, **новая** пара; старый refresh больше не действует |
| POST | `/logout` | — (нужен Bearer) | 204, отзыв **всех** токенов пользователя |

Ответ с токенами:

```json
{
  "data": {
    "access_token": "...",
    "refresh_token": "...",
    "token_type": "Bearer",
    "expires_in": 2592000
  }
}
```

`expires_in` — секунды жизни access (при текущих env ≈ 30 суток). Refresh живёт около года. Неверный логин — **422**, не 401. Невалидный refresh — 401.

На API нет `GET /user`, нет смены пояса и нет 2FA/passkey. Пояс профиля задаётся при регистрации; сменить его можно только в вебе.

Сброс пароля (`/password/forgot`, `/password/reset`) — письмо со ссылкой на веб. В клиент первой версии не тащим.

Лимиты: логин/регистрация — 5/мин на email+IP.

### Приступы

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/seizures` | Создать. 201 + ресурс |
| GET | `/seizures` | Список. `from`, `to` (`Y-m-d`), `timezone`, `per_page` (1–100, по умолчанию 50), `page` |
| PATCH | `/seizures/{id}` | Редактировать. 200 + ресурс. PUT-семантика: клиент всегда шлёт оба поля. Чужой/нет — 404 |
| DELETE | `/seizures/{id}` | Мягкое удаление. 204. Чужой/нет — 404 |
| GET | `/seizures/export.docx` | Экспорт периода в DOCX. Параметры периода — как у списка (`from`, `to`, `timezone`). 200 — бинарный DOCX, имя файла в `Content-Disposition`; 422 при невалидном периоде |
| POST | `/seizures/email-self` | Письмо с DOCX себе. Период — в query, тело пустое. 200 `{message}`. Лимит 5 писем/мин на пользователя, общий с веб-действиями |
| POST | `/seizures/email-doctor` | Письмо с DOCX врачу. Период — в query, тело: `to` (email, обязателен), `subject?`, `body?`. 200 `{message}`; 422 с `errors.to|subject|body` и/или ошибками периода. Тот же лимит 5/мин |

Нет `GET` по id. Редактирование — `PATCH` с PUT-семантикой: всегда отправляются оба поля `occurred_at` + `comment`; `comment: null` — очистить, `occurred_at: null` (или без поля) — «сейчас». Валидация и `timezone` — как у создания.

Ресурс приступа: `id`, `occurred_at`, `comment`, `created_at`. Моменты — UTC ISO-8601 с микросекундами (`…Z`). `user_id` и `deleted_at` не отдаются.

Создание: `occurred_at` (nullable), `comment` (nullable, max 2000), `timezone` (nullable, IANA). Пустое тело = сейчас. Нельзя записать момент больше чем на 5 минут в будущее (после нормализации в UTC).

Фильтр списка: `from`/`to` — целые дни в разрешённом поясе (запрос → иначе пояс пользователя → иначе UTC), границы включительно. Сортировка: `occurred_at` DESC, затем `id` DESC.

Экспорт и письма — те же DOCX и вложение, что в вебе; `timezone` запроса задаёт группировку дней документа. Печать — только веб.

### Токены и refresh

Access и refresh хранить в SecureStore, не в AsyncStorage.

На 401 защищённого запроса — один `POST /token/refresh`, подставить новую пару, повторить исходный запрос. Старый refresh после ротации бесполезен.

Ротация плюс «отозвать все access» — причина не плодить два процесса с копиями одних токенов. В одном приложении: **одна очередь refresh**, без параллельных вызовов.

Logout из журнала чистит локальные токены; быстрый вход после этого снова покажет логин.

## 8. Время

Сервер хранит и отдаёт UTC. Клиент:

- при записи быстрого события шлёт IANA пояса устройства;
- при записи задним числом из журнала — наивную дату/время **и** тот же `timezone` (так API и задуман);
- на экране конвертирует `occurred_at` из UTC в локальный пояс.

Строка с суффиксом `Z` или смещением парсится как абсолютный момент; переданный `timezone` тогда игнорируется.

## 9. Локальная разработка

Эмулятор Android не видит `localhost` машины разработчика. База API:

- эмулятор: `http://10.0.2.2:<порт>/api/v1`;
- телефон в той же сети: `http://<IP OpenServer>/api/v1`.

HTTP без TLS Android по умолчанию режет — для отладки нужен cleartext (настройка в app config), на проде только HTTPS.

OpenAPI/Swagger в серверном репозитории нет. Postman-коллекция описывает seizures и местами ещё cookie-эпоху; ориентироваться на фактические маршруты `/api/v1` и этот документ.

## 10. Вне первой версии

- Виджет рабочего стола и плитка в шторке — лучше, чем вторая иконка, но это уже native/config plugin; после того как быстрый вход заработает.
- Офлайн-буфер («накопил без сети, отправил пачкой») — в API пакетного create нет; либо очередь на клиенте по одному POST, либо отдельная доработка сервера.
- iOS — отдельное решение; Expo позволит, но сейчас не цель.
- Два APK с общим логином — только если появятся два листинга; тогда ContentProvider + одна подпись, не SecureStore между пакетами.

## 11. Порядок внедрения (когда заведём репозиторий)

1. Каркас Expo, логин/регистрация, SecureStore, обёртка API с одной очередью refresh.
2. Журнал: список + создание «сейчас» + удаление.
3. Вторая иконка и поток «Приступ» (§5).
4. Фильтр периода, задним числом, обработка ошибок и пустых состояний.
5. Dev/preview build на устройство, проверка против живого `/api/v1`.
