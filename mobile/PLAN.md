# План разработки мобильного клиента «График приступов»

> Раскладка: код и конфиги приложения лежат в этом репозитории в каталоге `mobile/`.
> Серверный контракт — Laravel JSON API под `/api/v1` (Sanctum + refresh).
> Документ-источник идеи: [`MOBILE.md`](../MOBILE.md). Этот файл — план реализации, а не его замена.

## 0. Опорные факты (что зафиксировано до планирования)

- **Стек клиента**: Expo SDK + TypeScript, навигация `expo-router`, токены в `expo-secure-store`, часовой пояс из `expo-localization`.
- **Платформа на первом этапе**: только Android. iOS не цель.
- **Две точки входа в одном APK**: основной лаунчер «Журнал» + `activity-alias` «Приступ» (через config plugin). Общая сессия в одном процессе.
- **API уже реализован** в этом же репозитории (`routes/api.php`, контроллеры `App\Http\Controllers\Api\V1\*`, `App\Services\TokenService`). Контракт брать из кода, не из воображения. Клиентские модели пишем руками (OpenAPI в репо нет).
- **Сетевая база для отладки**: эмулятор `http://10.0.2.2:<порт>/api/v1`, устройство в локальной сети — IP OpenServer. HTTP без TLS требует разрешения cleartext в `app.json` для debug-сборок, прод — только HTTPS.
- **Минимальная батарея тестов** согласуется с CLAUDE.md: не плодим лишнего, на каждом этапе — только тот тест, который ловит реальный регресс.

## 2. Этапы

Каждый этап — отдельный коммит на ветке `feature/mobile-stage-N`. Этап считается закрытым, только если выполнены его критерии приёмки и пройден `npm run lint:check && npm run types:check && npm run test` (после того как в этапе 0 подключим тесты). Шаги внутри этапа идут последовательно.

### Этап 0. Каркас проекта в `mobile/`

**Цель**: пустой Expo-проект, который запускается на Android-эмуляторе и не падает.

Шаги:
1. `npx create-expo-app mobile --template blank-typescript` (или эквивалент через `npm create expo`). Альтернативно — минимальный ручной `package.json` + `app.json`, без шаблона, чтобы не тащить чужой мусор.
2. `tsconfig.json` со strict, `paths` под `@/*` → `src/*`.
3. ESLint + Prettier, идентичные настройкам корня (`npm run lint`, `npm run format:check`).
4. `app.json`: имя «График приступов», bundle id (Android `package`), иконки, splash, `android.package`.
5. `eas.json` с тремя профилями: `development` (включает dev-client), `preview` (APK для раздачи), `production` (AAB).
6. `.gitignore` дополняем `mobile/.expo/`, `mobile/dist/`, `mobile/node_modules/`.
7. README в `mobile/README.md`: как поднять локально, какие URL ставить для эмулятора/устройства.

**Критерий приёмки**: `npx expo start` поднимает Metro; `expo prebuild --platform android` создаёт валидный Android-проект; пустое приложение запускается в эмуляторе.

### Этап 1. HTTP-клиент, токены, аутентификация

**Цель**: общая для журнала и быстрого входа сессия. Логин и регистрация работают против живого `/api/v1`.

Шаги:
1. `src/api/client.ts`: тонкая обёртка над `fetch` (или `ky`), читает `API_BASE_URL` из `src/config/env.ts`, всегда шлёт `Accept: application/json` и `Content-Type: application/json` где есть тело.
2. `src/auth/tokens.ts`: чтение/запись/очистка пары токенов в `expo-secure-store`. **Никогда** AsyncStorage. Запись — один ключ `auth.tokens` с атомарным JSON `{ access_token, refresh_token, email }` (решение по итогам этапа 1: два отдельных ключа оставляли бы окно несогласованного состояния при ротации, а email переносится между записями при refresh без повторного входа).
3. **Единая очередь refresh** (см. [`MOBILE.md`](../MOBILE.md) §7): при получении 401 на защищённом запросе — один-единственный `POST /token/refresh`, подставить новую пару, повторить исходный запрос. Параллельные 401 не плодят параллельных refresh — они ждут в очереди. Если refresh сам вернул 401 — чистим токены и эмитим событие «сессия истекла».
4. `src/api/auth.ts`: `register`, `login`, `logout`. Маппинг ответов: `data.access_token`, `data.refresh_token`, `data.expires_in`.
5. `AuthContext` + `useAuth()`: хранит `{ status: 'unknown' | 'anonymous' | 'authed', user? }`, делает bootstrap из SecureStore при старте приложения, пробрасывает методы логина/логаута.
6. Экраны `app/(auth)/login.tsx` и `app/(auth)/register.tsx`. Регистрация сразу шлёт `timezone` (IANA из `expo-localization`).
7. На login/register: 422 → показать field-ошибки; 429 → «слишком много попыток, подождите минуту»; сеть → «нет связи, повторить».

**Критерий приёмки**: запуск с эмулятора, регистрация нового пользователя, токены появились в SecureStore, рестарт приложения не спрашивает логин повторно. Ручная проверка: подменить access на мусор → следующий защищённый запрос сам уходит в refresh и проходит.

### Этап 2. Журнал: список, создание «сейчас», удаление

**Цель**: основной пользовательский сценарий работает целиком через иконку «Журнал».

Шаги:
1. `app/(journal)/_layout.tsx` со стеком.
2. `app/(journal)/index.tsx` — экран списка:
   - `GET /seizures?per_page=50&timezone=<IANA>` при монтировании и pull-to-refresh;
   - ресурс приступа: `id`, `occurred_at` (UTC ISO с `Z`), `comment`, `created_at` (`user_id`/`deleted_at` клиенту не отдаются — игнорируем);
   - `utils/time.ts`: парсер UTC ISO-8601 с микросекундами, отображение в локальном поясе устройства;
   - пустое состояние, ошибка сети, 401 после refresh — отдельные тексты.
3. `app/(journal)/new.tsx` — создать:
   - по умолчанию «сейчас» (`timezone` обязательно шлём, `occurred_at` пустое);
   - поле комментария (max 2000, счётчик);
   - кнопка «отменить», навигация назад после успешного 201.
4. Удаление через свайп/long-press с подтверждением → `DELETE /seizures/{id}`. Чужой/несуществующий — 404, текст «не найдено» без утечки информации.
5. `app/(journal)/settings.tsx` — профиль (минимум: email/logout) и кнопка «Выйти»: чистим токены, переходим на логин.

**Критерий приёмки**: цепочка «создать → увидеть в списке → удалить → список обновился» работает офлайн-эмулятор + живой API. Проверка на устройстве в локальной сети: `http://<IP OpenServer>/api/v1` отвечает.

### Этап 3. Вторая иконка и поток «Приступ»

**Цель**: быстрый вход «нажал — отправилось — закрылось».

Шаги:
1. Config plugin `plugins/activity-alias/`:
   - в `AndroidManifest.xml` добавляется `activity-alias` с собственным `android:label`, `android:icon`, `android:targetActivity=".MainActivity"` и фильтром `MAIN`/`LAUNCHER`;
   - маркер входа — не `Intent` extras (отклонение от исходной формулировки: лаунчер extras не шлёт): им служит сам компонент alias `.QuickEntryAlias` — патч `MainActivity` переводит его в `intent.data = seizure://quick`, дальше маршрут `/quick` разбирает штатный deep-link механизм expo-router;
   - ресурсы иконки: adaptive-icon `ic_launcher_quick` (тот же foreground, что у журнальной, фон-цвет); legacy-иконки кладутся во все плотности безусловно — в Expo 57 minSdk задаётся gradle-плагином, числа в `build.gradle` нет, поэтому на API < 26 иконка совпадает с журнальной (различие — только Android 8+).
2. `app.json` подключает plugin ссылкой на файл `"./plugins/activity-alias/plugin"` (резолвер Expo не находит `plugin.ts` при ссылке на директорию); пропс — `iconBackgroundColor` (`#C62828`; label «Приступ» зашит в plugin).
3. Отдельного чтения intent в корневом `app/_layout.tsx` нет: URL проставляет нативный патч из п.1, роутит штатный deep-link expo-router. В `_layout.tsx` — гард `returnTo=/quick` (аноним из `/quick` уходит на логин и после успеха возвращается в быструю ветку, не в журнал) и запрет жеста «назад» для `quick`. В dev-сборке (`expo prebuild && expo run:android`) проверяем, что в лаунчере **две** иконки.
4. `app/quick.tsx` (не `app/(quick)/index.tsx`: две группы `index.tsx` конфликтуют на пути «/»):
   - нет токенов → push в `/(auth)/login` (или `register`), после успеха сразу `POST /seizures`;
   - есть токены → сразу `POST /seizures` с `{ timezone }`;
   - 201 → `BackHandler.exitApp()` (Android) либо `finishAffinity` через нативный модуль, **никакого** журнала на экране;
   - 401 после refresh — показать текст «войдите снова» с кнопкой на логин; не закрывать молча;
   - сеть/5xx — кнопка «повторить».
5. `occurred_at` в быстром пути **не передаём** — это «прямо сейчас», согласно [`MOBILE.md`](../MOBILE.md) §5.

**Критерий приёмки**: на физическом Android две иконки в лаунчере; тап по «Приступ» при наличии сессии — запрос ушёл, экран закрылся; без сессии — короткий логин, потом запрос, потом выход.

> Замечание про Expo Go: в Expo Go `activity-alias` не появляется в лаунчере — это известное ограничение. Для проверки иконок обязателен development/preview build (`expo run:android` или EAS development build). Это явно отмечаем в `mobile/README.md`.

### Этап 4. Фильтр периода, задним числом, обработка ошибок

**Цель**: журнал становится пригодным для повседневного использования.

Шаги:
1. Фильтр в списке: «Сегодня / 7 дней / 30 дней / Произвольный период» → параметры `from`, `to` (`Y-m-d`) и `timezone`. Границы включительно — сервер сам разруливает; на клиенте только UI.
   - Дефолтное состояние фильтра — «Всё время» (без `from`/`to`); четыре опции из плана — выбор пользователя. Зафиксировано по итогам дизайн-ревью как сохранение поведения этапа 2 (список без ограничений до явного выбора периода).
2. Создание задним числом: в `app/(journal)/new.tsx` добавить переключатель «точное время» → date/time picker; в тело уходят наивная дата/время + `timezone` (логика API — нормализует в UTC, см. [`MOBILE.md`](../MOBILE.md) §8).
3. Серверное правило «не больше 5 минут в будущем» — на клиенте подсветить picker, не дать сохранить.
4. Обработка ошибок:
   - сетевая → «нет связи, повторить»;
   - 5xx → «сервер недоступен, повторите позже»;
   - 422 → подсветка полей;
   - 429 → «слишком часто, подождите»;
   - 401 после провала refresh → возврат на логин, без потери локального ввода где возможно.
5. Пустые состояния списка: «приступов пока нет» с подсказкой «нажмите + чтобы записать».

**Критерий приёмки**: фильтры реально меняют выборку (видно в логах запроса); запись задним числом с будущей датой невозможна через UI; сообщения об ошибках понятны без чтения исходников.

### Этап 5. Dev / preview build и смок против живого API

**Цель**: проверить всё на устройстве, а не только в эмуляторе. Это ворота к «готово к использованию».

Шаги:
1. `eas build --profile development --platform android` (или `expo run:android` для локальной сборки).
2. На устройстве в той же сети, что OpenServer: `API_BASE_URL=http://<IP>:8000/api/v1` (через `.env` в `mobile/.env` или dev-client config).
3. Чек-лист ручных проверок (одноразовый, после — можно автоматизировать частично):
   - [ ] иконка «Журнал» открывает список;
   - [ ] иконка «Приступ» при наличии сессии отправляет POST и закрывает приложение;
   - [ ] иконка «Приступ» без сессии ведёт через логин/регистрацию и затем закрывается;
   - [ ] рестарт приложения не требует повторного логина;
   - [ ] удаление работает; 404 на чужой id не падает;
   - [ ] фильтр периода реально меняет запрос;
   - [ ] запись задним числом не позволяет будущее > 5 мин;
   - [ ] kill процесса во время refresh не оставляет приложение в «зависшем» состоянии (следующий запуск — чистый bootstrap).
4. Фиксы по результатам, отдельным коммитом.

**Критерий приёмки**: чек-лист пройден на физическом Android. После этого — можно отдавать на ежедневное пользование.

## 3. Сквозные правила (применяются на всех этапах)

- **Никакого `localhost`** в клиентском коде. База берётся из `src/config/env.ts` и зависит от `APP_ENV` (dev / preview / production) и платформы (эмулятор vs устройство). Документируем в `mobile/README.md`.
- **Только HTTPS в проде**. В debug-сборках разрешаем cleartext для конкретного домена (через `android.networkSecurityConfig` в plugin) — и только для debug-варианта.
- **Refresh — одна очередь** (см. Этап 1, п.3). Не плодим параллельных refresh ни в каком сценарии. Это требование из [`MOBILE.md`](../MOBILE.md) §7, нарушение ломает «отозвать все access».
- **Никаких третьесторонних state-менеджеров** на старте. React Context + reducer хватает; добавляем zustand/redux только если появится реальная боль.
- **Никакой бизнес-логики в компонентах** — только вызовы из `src/api/*` и `src/utils/*`. Всё, что можно протестировать без UI, выносим в `src/utils` и `src/api`.
- **Тесты — только там, где они ловят реальный регресс**: парсер времени, refresh-очередь, http-обёртка (моки). UI-тесты не пишем на этом масштабе (согласно CLAUDE.md «Minimal test coverage»).
- **Документация**: `mobile/README.md` — как поднять, как собрать, как выгрузить; `mobile/PLAN.md` (этот файл) — план; правки контракта API идут в [`MOBILE.md`](../MOBILE.md) §7 и в код `routes/api.php`.

## 4. Что осознанно НЕ делаем в v1

Список из [`MOBILE.md`](../MOBILE.md) §10 плюс уточнения по этой раскладке:

- **iOS** — отдельное решение позже; Expo это позволит без переписывания.
- **Виджет / плитка в шторке** — после стабилизации быстрого входа.
- **Офлайн-буфер** — в API нет пакетного create. Либо клиентская очередь по одному POST (отдельный этап, не v1), либо доработка сервера.
- **Сброс пароля** — на API это ссылка на веб; в мобильный клиент первой версии не тащим.
- **2FA/passkey** — на API отсутствуют; клиент их не выдумывает. Профильные эндпоинты позже появились (`/profile`: чтение, смена `name`/`email`/`timezone`, удаление аккаунта — контракт в [`MOBILE.md`](../MOBILE.md) §7); `GET /user` по-прежнему нет.
- **Два APK / два листинга** — нужны только при появлении разных аудиторий; сейчас лишнее.
- **OpenAPI-генерация клиента** — контракт в репо не хранится, моделей мало, руками проще и честнее.

## 5. Порядок закрытия этапов и критерии «готово»

| Этап | Что доказано | Готово когда |
|---|---|---|
| 0 | Expo-каркас запускается в эмуляторе | `expo prebuild` валиден, Metro поднимается, пустое приложение видно |
| 1 | Сессия живёт между запусками, refresh один на всех | ручной чек + unit на refresh-очередь |
| 2 | CRUD журнала работает против живого API | ручной сценарий + unit на парсер времени |
| 3 | «Приступ» закрывает приложение после 201 | две иконки в лаунчере физического Android, оба сценария (с/без сессии) |
| 4 | Журнал пригоден для ежедневного использования | фильтры, задним числом, ошибки не молчат |
| 5 | Сборка на устройстве проходит смок | чек-лист Этапа 5 закрыт |

После Этапа 5 — мобильный клиент v1. Дальше: задачи из §4 по приоритету пользователя.

## 6. Открытые вопросы, которые решим до Этапа 3

1. **Bundle id** Android: `com.<user>.seizure` или иной? Берём из уже существующих настроек проекта, если есть; иначе — спросить.
2. **Иконки**: готовим две (`journal`, `quick`) или пока одну, а вторую подменим позже? В плане заложены две, но финальные PNG/Adaptive Icon нужны до Этапа 3.
3. **Где хранить `API_BASE_URL`**: `.env` в `mobile/` (через `expo-constants` + `extra`) или в `app.json` под `extra`? Дефолт — `extra` в `app.json`, перебивается переменной окружения при сборке.
4. **Push-уведомления / виджет**: подтверждаем, что это v2, а не v1 (по [`MOBILE.md`](../MOBILE.md) §10 — да, v2).
